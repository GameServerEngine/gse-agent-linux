# Changelog

Each fixed issue gets an entry under the version that shipped it: a one-line title, then the cause and the fix in plain language, written so a customer can follow it.

## Unreleased
- **Status samples report every game server's CPU, RAM and disk, and every other container:** the panel only saw the five busiest processes of the whole machine, so it could not tell how much one game server uses. The status sample now adds one line per game server (its state, CPU and RAM of the game and bot with their child processes and its own container, and the folder size measured in the background once an hour) and one line per Docker container that is not a game server's own, with its name, image, CPU, RAM and main process.
- **An update no longer fails when it replaces its own helper:** the update helper is one of the files an update replaces, and it replaced itself while it was running. Bash reads a script as it goes, so when the new file was a different size the old helper carried on reading from the wrong place. Depending on the change it ran steps twice, or stopped half way with the update stuck on "running" and the old code still in place. The whole update now runs from one function that bash has read completely before the first step, so replacing the file cannot change what runs. This protects updates made from this version onward.
- **An update no longer leaves the old agent code running:** after a release update the panel said "Agent updated and running" while the agent was still running the old code. The update stopped only the agent program, and the script that keeps it alive started it again ten seconds later, in the middle of the file copy, so the new files were never loaded. The update now makes that script wait until the new files are in place, then checks that the running agent started after the copy and restarts it if not, and only then reports success. The fix protects updates made from this version onward, because an update is run by the helper that is already installed.
- **The agent reports its hardware:** the new read-only `agent_hardware_inventory` call returns the CPU model and allowed CPUs, any CPU or memory limit, memory, the game volume and the disks. Anything the machine does not tell us is reported as unknown, never as zero. The panel uses it to plan where games can run.
- **Container start for a server that never ran natively:** the start failed with "Agent did not answer" because the agent told the native watchdog to stand down before it had recorded where the server lives. The server is now recorded first.
- **Console logs are read safely (security):** reading a server's console log ran `chmod 777` as root on a file the customer could replace with a link, and passed the file name to a shell. A plugin could use this to take over the machine or read the agent's key. Logs are now read as the server's own user, links are refused, and nothing is passed to a shell.
- **Server folder permissions are fixed safely (security):** fixing permissions passed customer file names to root `chmod` through a shell, so a file named like a system path could change that system file. Names are now passed as arguments only. The start script is no longer written through links.
- **Game servers can run in Docker containers:** an admin can choose Docker for a server. The server keeps its folder, FTP, file manager, ports and startup line; the game runs as the server's own user with no extra rights, cannot see other servers, the agent or the host, and has CPU, RAM and process limits. Native stays the default. Set up a node with `scripts/gse_container_host.sh`.
- **Linux version numbers match Windows:** the Linux agent restarts its numbering at 1.5.3, the same as the Windows agent. Linux agents numbered 0.x are old and should be updated.
- **Steam installs on Linux:** SteamCMD is told to download the Linux build, and a Steam Guard code is sent only for a real Steam account. Anonymous installs such as Counter-Strike: Source (AppID 232330) no longer fail with "Missing configuration".
- **Docker container RPCs, as on Windows:** the opt-in `container_*` RPCs and `GSE/Container/Runtime.pm` (the same file as the Windows agent) are now in the Linux agent. They are off unless `container_runtime_enabled` is `1`, and they do not change how normal game servers run.
- **Container commands report their real result:** Docker commands run by the container RPCs were always reported as failed (exit code 72057594037927935), because the agent ignores child exits and so lost each command's exit code. The command runner now reads the real exit code. Fixed in the shared file, so the Windows agent gets it too.
- **Protocol version:** `agent_version` and `agent_resource_snapshot` now return `protocol_version`, like the Windows agent, so the panel can check it before an update.
- **Agent update works:** a release download that worked was reported as "Could not download the release archive", because the agent read the download's exit code wrongly. It now reads the real one.
- **Runs games like the Windows agent:** Start, Stop, Force Stop, Restart, status and a check every 5 seconds now use `GameManager.pm`, the same file as the Windows agent; `GameManagerLinux.pm` does the Linux process and port checks. A server wanted RUNNING is started or adopted after an agent restart or a reboot, the game port is freed before a launch, a start that does not answer on its port within 5 minutes is retried once, a game that dies is restarted at once after three missed checks (5 crashes in 30 minutes leave it FAILED), and a clean exit (code 0) is relaunched without counting a crash. The old bash watchdog stopped a server for good when its game died within 120 seconds. Games still run in screen as their own user, so they keep running when the agent stops, and the panel's console and log work as before.
- **Game folder:** the game files are in `<server folder>/gamefiles`, as on Windows (it was `<server folder>/<game key>`).
- **Pre-start commands and environment variables:** kept from the game config, with the CPU and priority settings, in `gse_prestart.sh`, and run before every launch, also automatic restarts.
- **Start and stop on the host:** each server folder gets `startserver.sh` and `stopserver.sh`, which record RUNNING or STOPPED through `gse_ctl.pl`; the bot is `_alsoRun.sh` and runs only while its game is RUNNING. New `set_desired` RPC.
- **Restart without a wait:** Restart starts the game right after the stop. The 60 second wait outlived the panel's request, so the start never ran and the server was left stopped.

## 0.5.1
- **One-file installer:** `gse-agent-linux-install.sh` (attached to every release) asks for the panel address, the agent key from the panel's Servers page and the agent user's password; gets the server's settings and the release from the panel; installs the prerequisites, creates the user, writes the configuration, sets up Pure-FTPd, installs and starts the systemd service and tells the panel the agent is ready. Tested on Ubuntu 24.04 and Debian 12 against a test panel.
- **The panel finds the agent's IP addresses:** the IP list came from parsing `/sbin/ifconfig`, which current Ubuntu and Debian do not install, so a new server got no IPs. It now reads `ip -o -4 addr show`.
- **Agent stops at once:** `systemctl stop` and `restart` took 60 seconds because the start script ignored the stop signal and restarted the agent. It now passes the signal on and exits.
- **Installer:** a failed clone in non-interactive mode stops after 3 tries instead of retrying forever, and root can clone a source folder owned by another user. The prerequisite installer no longer exits at the i386 question when it has no keyboard (it takes the default, yes).
- **Requirements:** minimum is Ubuntu 22.04 or Debian 12 (tested in containers: the prerequisites install and the agent compiles).
- **A dead watchdog is brought back:** Every 30 seconds the agent checks each game that is wanted RUNNING. If its watchdog is gone (killed, or lost after a crash) it starts the watchdog again with `serverStart.sh start`. The watchdog takes over a game that is still up on its port (it is not killed), or launches it. A game wanted STOPPED is never touched, and each game is revived at most once a minute. Before this, the Panel showed OFFLINE or a warning while the status said RUNNING, until someone pressed Start.
- **Stop said "stopped" while the game kept running; Start then failed with the port in use:** When a game was left running without its watchdog (the watchdog was killed, or the agent restarted), the agent could not see the game. It runs as its own Linux user (`gamehomeNNN`), and the agent user cannot read that user's process details. So it did not find the game on its port, thought the game was dead, never killed it, and still reported success. The agent now looks up port owners and process details with sudo, treats a process it may not signal as alive, and counts a listening port as "still running" even when it cannot name the owner.
- **Kill really kills:** The agent's kill step sent `kill 15 <pid>`, which is not a TERM signal to that process, and ran as the wrong user when no screen session was left. It now sends TERM as root, waits up to 5 seconds, and then sends KILL.
- **Agent refused to start on a fresh install:** The start-up check for a missing agent key also matched the empty `web_admin_api_key` line in the default config, so a correctly configured agent was rejected as having a placeholder key. The check now only looks at the `key` line itself.
- **Start and stop on the host:** Each game folder now gets `startserver.sh` and `stopserver.sh`. They do the same as the Panel Start and Stop (they call `serverStart.sh start` or `stop`), so the status files stay correct when an admin starts or stops a game on the host. Closing the game by hand while it is wanted RUNNING still gets it restarted; use `stopserver.sh`.
- **Requirements file:** `requirements.json` lists the prerequisites for the website to show. Minimum is Ubuntu 22.04 or Debian 12; tested on Ubuntu 24.04 LTS with a game, and Ubuntu 22.04 and Debian 12 in containers.
- **One action at a time per server:** Start and Stop on the host take a per-server lock (`status.lock`), so two of them, or one with the Panel, cannot overlap and launch a second copy.
- **Status follows the real game:** The game port is now passed to the watchdog, which uses it to tell whether the game is really up, in the same way as the Windows agent. Tests: `tests/validate_status_follows_reality.sh`.
